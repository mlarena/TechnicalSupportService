Ниже представлен **проект технического задания (ТЗ)** на разработку приложения для службы технической поддержки. ТЗ составлено в формате, принятом в российской ИТ-индустрии, с детальной проработкой требований к данным, логике нумерации, версионности и истории.

---

# ТЕХНИЧЕСКОЕ ЗАДАНИЕ  
на разработку веб-приложения «Система управления технической поддержкой» (СУТП)
имя решения TechnicalSupportService.

## 0. Структура решения (проекты)

Решение (`TechnicalSupportService.sln`) состоит из трёх проектов:

| Проект | Тип | Назначение |
|--------|-----|------------|
| **TechnicalSupportService.Data** | Class Library (.NET 10) | Сущности (Entities), DbContext, миграции EF Core, enum'ы, конфигурации маппинга (Fluent API) |
| **TechnicalSupportService.Core** | Class Library (.NET 10) | Интерфейсы сервисов (IService), DTO/ViewModels, бизнес-правила и валидация, вспомогательные утилиты. **Не зависит** от Data и SUTP |
| **TechnicalSupportService.SUTP** | ASP.NET Core MVC Web App (.NET 10) | Контроллеры, Razor Views, реализации сервисов, wwwroot (CSS/JS), конфигурация DI, Identity, запуск приложения |

### Зависимости между проектами

```
TechnicalSupportService.Core  (нет зависимостей)
        ↑
TechnicalSupportService.Data  (зависит от Core — использует интерфейсы и DTO)
        ↑
TechnicalSupportService.SUTP  (зависит от Data и Core — подключает DI, реализует сервисы)
```

## 1. Введение
### 1.1. Назначение
Разработать корпоративное веб-приложение для автоматизации процессов приёма, учёта, обработки и хранения заявок в службе технической поддержки компании, которая разрабатывает ПО и технические изделия.

### 1.2. Цели
- Централизованное хранение заявок и сопутствующих документов.
- Разграничение доступа по ролям.
- Полная история изменений по каждой заявке.
- Уникальная, человеко-читаемая нумерация заявок с ежемесячным сбросом.

---

## 2. Общие требования к системе
### 2.1. Архитектура
- **Бэкенд:** .NET 10 (Core), ASP.NET Core MVC.
- **ORM:** Entity Framework Core 10.
- **БД:** PostgreSQL 16+.
- **Фронтенд:** Razor Pages / MVC Views + Bootstrap (допускается использование HTMX для динамики, но не обязательно).
- **Аутентификация:** ASP.NET Core Identity с кастомизацией.
- **Общий вид:** возможность изменять темы - светлая темная.

### 2.2. Требования к развертыванию
-  Linux debian (контейнеризация Docker – опционально).
- Конфигурация через `appsettings.json` и переменные окружения.

## 3. Функциональные требования

### 3.1. Авторизация и управление пользователями
- Регистрация / вход по email и паролю.
- Подтверждение email (опционально, но желательно).
- Восстановление пароля.
- Администратор может:
  - Создавать/редактировать/блокировать/удалять пользователей.

### 4.2. Версионность и история изменений

#### 4.2.1. Таблица `TicketHistory`
Каждое изменение заявки фиксируется в отдельной таблице.

| Поле                  | Тип данных | Описание                                        |
|-----------------------|------------|-------------------------------------------------|
| **Id**                | UUID (PK)  | Уникальный идентификатор записи истории         |
| **TicketId**          | UUID (FK)  | Ссылка на заявку                                |
| **ChangedByUserId**   | UUID (FK)  | Кто изменил                                     |
| **ChangedAt**         | Timestamp  | Дата изменения (UTC)                            |
| **FieldName**         | String(50) | Название изменённого поля (например, `Status`)  |
| **OldValue**          | Text       | Старое значение (в виде строки)                 |
| **NewValue**          | Text       | Новое значение (в виде строки)                  |
| **ChangeType**        | Enum       | `Update` / `Comment` / `FileAttach` / `StatusChange` |

#### 4.2.2. Правила фиксации
- Изменение **любого поля** → новая запись в `TicketHistory`.
- Добавление комментария → запись с `ChangeType = Comment`.
- Прикрепление/удаление файла → запись в истории.

#### 4.2.3. Просмотр истории
На странице заявки предусмотреть вкладку **«История»**, где отображается хронологический список всех изменений с указанием:
- даты и времени (по локальному времени пользователя),
- ФИО пользователя,
- что именно изменилось (старое → новое),
- тип изменения.

### 4.3. Нумерация заявок (ключевое требование)

**Формат номера:**  
`ГГГГ_ММ_ПОРЯДКОВЫЙ_НОМЕР`

Примеры:
- `2026_08_001`
- `2026_08_102`
- `2026_09_001` (сброс в новом месяце)

**Правила генерации:**
1. Номер формируется **автоматически** при создании заявки.
2. Счётчик сбрасывается **каждый месяц** (независимо для каждого месяца).
3. Счётчик хранится в отдельной таблице `TicketNumberCounter`:
   - `YearMonth` (например, `2026-08`) – PK.
   - `LastNumber` – последний использованный номер.
4. При создании заявки в транзакции:
   - Блокируем строку `SELECT ... FOR UPDATE`.
   - Инкрементируем `LastNumber`.
   - Формируем номер: `$"{Year:0000}_{Month:00}_{LastNumber:D3}"`.
   - Если строка отсутствует – создаём со значением `1`.
5. Допустимо использование `SEQUENCE` с условием, но рекомендуемый подход – таблица с блокировкой для простоты и ясности.

## 5. Хранение документов (файлов)

### 5.1. Требования
- Каждый файл прикрепляется к конкретной заявке.
- Поддерживаемые форматы: `.pdf`, `.doc`, `.docx`, `.xls`, `.xlsx`, `.jpg`, `.png`, `.zip` (можно расширить).
- Максимальный размер одного файла – **50 МБ**.
- Общий лимит на заявку – **500 МБ**.

### 5.2. Хранение
- Физические файлы хранятся на файловом сервере (или в облачном хранилище S3-совместимом).

|----------------------|------------|------------------------------------------|
| **Id**               | UUID (PK)  | Идентификатор                            |

| **FileSizeBytes**    | BigInt     | Размер в байтах                          |
| **MimeType**         | String(100)| MIME-тип                                 |

## 6. Бизнес-логика и статусная модель

### 6.1. Диаграмма состояний (переходы)

```
[New] → [Assigned] → [InProgress] → [Resolved] → [Closed]
  ↑         ↓              ↓            ↓
  └────[Reopened] ←─────────────────────┘
```

### 6.2. Правила переходов
- `New` → `Assigned` – назначается инженер (только менеджер или администратор).
- `Assigned` → `InProgress` – инженер начал работу.
- `InProgress` → `Resolved` – инженер предоставил решение (заполняет `Resolution`).
- `Resolved` → `Closed` – заявитель или менеджер подтверждает закрытие.
- `Resolved` → `Reopened` – если проблема не решена (только заявитель или менеджер).
- `Closed` → `Reopened` – если проблема возникла снова (только заявитель или менеджер).
- Любой статус → `Closed` (только администратор или менеджер с комментарием).

## 7. Интерфейс пользователя (основные экраны)

### 7.1. Дашборд
- Сводка по статусам (количество заявок в каждом статусе).
- Список последних заявок (по 5–10 штук).
- Фильтры: по статусу, приоритету, назначенному инженеру, продукту.

### 7.2. Список заявок (таблица)
- Колонки: №, Заголовок, Статус, Приоритет, Продукт, Назначен, Дата создания.
- Поиск по номеру, заголовку, описанию.
- Пагинация (20 записей на страницу).
- Возможность экспорта в Excel/CSV (только для менеджера и админа).

### 7.3. Создание заявки
- Форма со всеми полями (обязательные помечены *).
- Выбор продукта из справочника (загружается из БД).
- Загрузка вложений (drag-and-drop или через кнопку).
- После сохранения – редирект на страницу заявки.

### 7.4. Просмотр заявки (детальная страница)
- Вся информация о заявке (все поля).
- Блок с прикреплёнными файлами (скачивание, удаление – по правам).

- Вкладка «История» с полной хронологией изменений.
- Кнопки действий (в зависимости от роли и статуса):
  - Редактировать (ограниченный набор полей).
  - Назначить исполнителя.
  - Изменить статус.
  - Закрыть заявку.

### 7.5. Личный кабинет пользователя
- Профиль (ФИО, email, отдел, контактный телефон).
- Настройка уведомлений (опционально).
- Список «Мои заявки» (созданные и/или назначенные).

## 8. Технические требования к БД (PostgreSQL)

### 8.1. Индексы
- `IX_Ticket_Number` – уникальный (для быстрого поиска по номеру).
- `IX_Ticket_CreatedAt` – для сортировки.
- `IX_Ticket_Status` – для фильтрации.
- `IX_Ticket_AssignedToUserId` – для выборки по исполнителю.
- `IX_TicketHistory_TicketId_ChangedAt` – для истории.
- `IX_Attachments_TicketId` – для загрузки файлов.

### 8.2. Триггеры (опционально)
- Автоматическое заполнение `UpdatedAt` при изменении строки.
- Автоматическое заполнение `CreatedAt` при вставке.

### 8.3. Sequence для счётчика заявок (альтернативный вариант)
Можно использовать одну последовательность, но тогда номер не будет сбрасываться ежемесячно. Поэтому рекомендуется таблица `TicketNumberCounter` с блокировкой на уровне строк.

## 14. Приложение: Полное описание всех таблиц БД

### 14.1. Таблица `Users` (расширение ASP.NET Identity)

Наследуется от `IdentityUser<Guid>`. Стандартные поля Identity (Id, UserName, Email, PasswordHash, PhoneNumber и др.) дополняются кастомными.

| Поле | Тип данных | Обязательное | Описание |
|------|-----------|--------------|----------|
| **Id** | UUID (PK) | Да | Уникальный идентификатор (наследуется от IdentityUser) |
| **FullName** | String(200) | Да | ФИО пользователя (Фамилия Имя Отчество) |
| **DepartmentId** | UUID (FK) | Нет | Ссылка на отдел (таблица `Departments`) |
| **Position** | String(100) | Нет | Должность |
| **IsActive** | Boolean | Да | Активен/заблокирован (по умолчанию `true`) |
| **CreatedAt** | Timestamp | Да | Дата создания учётной записи (UTC) |
| **UpdatedAt** | Timestamp | Да | Дата последнего обновления профиля (UTC) |

> Примечание: поля `Email`, `PhoneNumber`, `UserName`, `EmailConfirmed`, `PasswordHash` и др. наследуются от `IdentityUser<Guid>` и не дублируются.

---

### 14.2. Таблица `Departments` (справочник отделов)

| Поле | Тип данных | Обязательное | Описание |
|------|-----------|--------------|----------|
| **Id** | UUID (PK) | Да | Уникальный идентификатор |
| **Name** | String(200) | Да | Наименование отдела (уникальное) |
| **Description** | String(500) | Нет | Описание отдела |
| **IsActive** | Boolean | Да | Активен/архив (по умолчанию `true`) |
| **CreatedAt** | Timestamp | | Дата создания записи |

### 14.3. Таблица `Products` (справочник продуктов)

Вынесена из Tickets для нормализации. Ранее `ProductName` и `ProductType` хранились прямо в заявке — теперь это FK.

| Поле | Тип данных | Обязательное | Описание |
|------|-----------|--------------|----------|
| **Id** | UUID (PK) | Да | Уникальный идентификатор |
| **Name** | String(200) | Да | Наименование продукта (например, "CRM v3.2", "Контроллер Т-100") |
| **ProductType** | Enum | Да | `Software` / `Hardware` / `Embedded` |
| **CurrentVersion** | String(20) | Нет | Текущая актуальная версия продукта |
| **Description** | String(500) | Нет | Краткое описание продукта |
| **IsActive** | Boolean | Да | Активен/снят с поддержки (по умолчанию `true`) |
| **CreatedAt** | Timestamp | Да | Дата создания записи |
| **UpdatedAt** | Timestamp | Да | Дата последнего обновления |

### 14.4. Таблица `Tickets` (заявки) — основная сущность

| Поле | Тип данных | Обязательное | Описание |
|------|-----------|--------------|----------|
| **Id** | UUID (PK) | Да | Внутренний идентификатор |
| **Number** | String(50) | Да | Внешний номер формата `ГГГГ_ММ_XXX` (unique index) |
| **Title** | String(200) | Да | Краткий заголовок заявки |
| **Description** | Text | Да | Полное описание проблемы |
| **ProductId** | UUID (FK -> Products) | Да | Ссылка на продукт (заменяет старые ProductType + ProductName) |
| **Version** | String(20) | Нет | Версия продукта, к которой относится заявка (может отличаться от CurrentVersion) |
| **Priority** | Enum | Да | `Low` / `Medium` / `High` / `Critical` |
| **Status** | Enum | Да | `New` / `Assigned` / `InProgress` / `Resolved` / `Closed` / `Reopened` |
| **Category** | Enum | Да | `Bug` / `Feature` / `Support` / `Incident` |
| **Impact** | Enum | Нет | `Individual` / `Team` / `Department` / `Company` |
| **Source** | Enum | Да | `Email` / `Phone` / `Portal` / `Internal` |
| **AssignedToUserId** | UUID (FK -> Users) | Нет | Исполнитель (инженер). Назначается менеджером/админом |
| **CreatedByUserId** | UUID (FK -> Users) | Да | Кто создал заявку (автозаполнение) |
| **CreatedAt** | Timestamp | Да | Дата создания (UTC) |
| **UpdatedByUserId** | UUID (FK -> Users) | Да | Кто последним изменял (автозаполнение) |
| **UpdatedAt** | Timestamp | Да | Дата последнего изменения (UTC) |
| **ClosedAt** | Timestamp | Нет | Дата закрытия (заполняется при статусе `Closed`) |
| **Resolution** | Text | Нет | Описание решения (заполняется при `Resolved` / `Closed`) |
| **TimeSpentMinutes** | Integer | Нет | Затраченное время в минутах (заполняется инженером) |
| **ParentTicketId** | UUID (FK -> Tickets) | Нет | Ссылка на родительскую заявку (для связи эпик/подзадача) |
| **IsDeleted** | Boolean | Да | Мягкое удаление (по умолчанию `false`) |
| **DeletedAt** | Timestamp | Нет | Дата удаления |
| **DeletedByUserId** | UUID (FK -> Users) | Нет | Кто удалил (заполняется при IsDeleted = true) |

> Изменение по сравнению с черновиком: `ProductName` (String) и `ProductType` (Enum) заменены на `ProductId` (FK -> Products). Это обеспечивает целостность справочника и возможность фильтрации по продукту.

### 14.5. Таблица `Comments` (комментарии к заявкам)

Вынесена из `TicketHistory` в отдельную сущность для удобства отображения и поиска.

| Поле | Тип данных | Обязательное | Описание |
|------|-----------|--------------|----------|
| **Id** | UUID (PK) | Да | Уникальный идентификатор |
| **TicketId** | UUID (FK -> Tickets) | Да | Заявка, к которой относится комментарий |
| **AuthorUserId** | UUID (FK -> Users) | Да | Автор комментария |
| **Content** | Text | Да | Текст комментария |
| **IsInternal** | Boolean | Да | Внутренний комментарий (виден только инженерам и менеджерам, не виден заявителю). По умолчанию `false` |
| **IsEdited** | Boolean | Да | Был ли отредактирован (по умолчанию `false`) |
| **EditedAt** | Timestamp | Нет | Дата последнего редактирования |
| **CreatedAt** | Timestamp | Да | Дата создания (UTC) |
| **IsDeleted** | Boolean | Да | Мягкое удаление (по умолчанию `false`) |

> При добавлении комментария в `TicketHistory` создаётся запись с `ChangeType = Comment` (ссылка на Id комментария в `NewValue`), но сам текст хранится в `Comments`.

### 14.6. Таблица `TicketHistory` (история изменений)

| Поле | Тип данных | Обязательное | Описание |
|------|-----------|--------------|----------|
| **Id** | UUID (PK) | Да | Уникальный идентификатор записи истории |
| **TicketId** | UUID (FK -> Tickets) | Да | Ссылка на заявку |
| **ChangedByUserId** | UUID (FK -> Users) | Да | Кто изменил |
| **ChangedAt** | Timestamp | Да | Дата изменения (UTC) |
| **FieldName** | String(50) | Нет | Название изменённого поля (для `ChangeType = Update` / `StatusChange`) |
| **OldValue** | Text | Нет | Старое значение (в виде строки). Null для первичного создания |
| **NewValue** | Text | Нет | Новое значение (в виде строки) |
| **ChangeType** | Enum | Да | `Update` / `Comment` / `FileAttach` / `StatusChange` / `Assignment` / `Creation` |
| **CommentId** | UUID (FK -> Comments) | Нет | Ссылка на комментарий (если `ChangeType = Comment`) |
| **AttachmentId** | UUID (FK -> Attachments) | Нет | Ссылка на вложение (если `ChangeType = FileAttach`) |

> Дополнение: новые значения `ChangeType`:
> - `Creation` — создание заявки (первая запись в истории);
> - `Assignment` — назначение/смена исполнителя.
> Добавлены FK на `CommentId` и `AttachmentId` для удобства навигации из истории.

### 14.9. Таблица `AuditLog` (аудит действий пользователей)

Отдельная таблица для логирования всех действий (§9 ТЗ — аудит). В отличие от `TicketHistory`, хранит **все** действия пользователей, не только изменения заявок.

| Поле | Тип данных | Обязательное | Описание |
|------|-----------|--------------|----------|
| **Id** | UUID (PK) | Да | Уникальный идентификатор |
| **UserId** | UUID (FK -> Users) | Да | Кто выполнил действие |
| **Action** | String(100) | Да | Тип действия (например, `Ticket.Create`, `User.Block`, `File.Upload`) |
| **EntityName** | String(100) | Нет | Имя сущности (`Ticket`, `User`, `Attachment` и т.д.) |
| **EntityId** | UUID | Нет | Идентификатор затронутой сущности |
| **Details** | Text | Нет | Дополнительные детали (JSON или текст) |
| **IpAddress** | String(45) | Нет | IP-адрес пользователя |
| **UserAgent** | String(500) | Нет | User-Agent браузера |
| **CreatedAt** | Timestamp | Да | Дата и время действия (UTC) |
